## 4. High-priority findings

### P1 — Evaluation conflates confluence score with probability

`evaluation.py` documents and implements the strategy score as a win probability, then calculates Brier score and calibration buckets from it. A confluence score is not a calibrated probability. This can make the evaluation output look statistically meaningful without a valid probability model.

**Required correction:** preserve raw score and confluence score as separate fields; only accept a probability from a versioned, validated calibration/model process; record predictions before outcomes; add time-ordered out-of-sample and walk-forward evaluation; report insufficient sample/data as unavailable rather than implying calibration.

### P1 — Missing market quotes can be represented by derived values

`CCXTFeed.snapshot()` substitutes bid/ask estimates around last price when provider quote fields are absent. Those derived values can pass the quote validity check while the snapshot source still appears to be the exchange feed.

**Required correction:** preserve quote provenance and validity explicitly. Missing provider quotes must be marked unavailable/estimated and must not be presented as observed exchange quotes. The data-quality policy should decide whether the snapshot is usable.

### P1 — Data-quality validation needs finite-value and field-completeness checks

The inspected `DataQualityGate` checks nulls, several high/low/close relationships, timestamps, volume ratio, freshness, price jumps, spread, and quote ordering. The checks do not visibly establish finiteness and positivity for every OHLCV field (notably open, all volume values, and timestamp values).

**Required correction:** add explicit finite-value checks and complete OHLCV invariants, including non-negative volume and valid timestamps. Add adversarial tests for NaN, positive/negative infinity, zero/negative prices, invalid bid/ask, and malformed CSV input.

### P1 — LIVE implementation and documentation contradict one another

The README and several configuration/deployment comments describe a package that refuses or does not contain live execution. However, `live.py` contains an exchange order-submission implementation and `execution.py` can construct that broker from configuration. The static UI and other documentation also describe the mode inconsistently.

**Required correction:** reconcile all documentation with the actual architecture. Keep any live-capable integration isolated and locked during development; all tests must use mocks or offline simulation. No real orders, real account credentials, or real balances are to be used in development validation.

### P2 — CI is useful but narrow

The current CI covers Python 3.11/3.12 unit tests and an offline smoke run. It does not currently show dedicated lint, type-check, coverage, dependency audit, or static security-analysis stages.

**Required correction:** add non-destructive quality gates incrementally, without weakening or deleting existing tests.

### P2 — Provider-dependent intelligence must be labelled clearly

News sentiment is lexicon-based and the on-chain engine relies on supplied data. These are valid deterministic components, but they are not equivalent to a continuously connected institutional news/on-chain feed.

**Required correction:** expose provider, timestamp, source, sample sufficiency, validity, and limitation metadata; show unavailable/not-calculated states when inputs are missing.

### P2 — Research engine is not yet evidenced at the V2 target level

Historical replay exists, but the inspected evaluation module does not implement a full train/validation/out-of-sample workflow, walk-forward analysis, parameter stability, or Monte Carlo research reporting.

**Required correction:** extend the existing replay/evaluation architecture rather than replacing it. Keep execution simulation deterministic and conservative, with explicit fees, spread, slippage, and intrabar assumptions.

## 5. Architecture and preservation notes

- Retain existing modules and public interfaces unless a compatibility-preserving migration is documented.
- Keep the PaperBroker, historical replay, current indicators, strategy, risk, analytics, portfolio, dashboard, logging, monitoring, and deployment components.
- Do not replace the current application with a new scaffold.
- Treat the static GitHub Pages demo as a separate browser-side simulation, not proof that the Python backend is deployed or connected.
- Keep demo records and any restricted execution records isolated by mode; do not infer isolation solely from a UI label.

## 6. Recommended implementation sequence

1. Add explicit tests for market-data validity, quote provenance, and non-finite values.
2. Correct evaluation semantics: score is not probability; add versioned prediction records and honest calibration states.
3. Complete deterministic research evaluation: time splits, out-of-sample reports, walk-forward support, and leakage tests.
4. Reconcile LIVE architecture/documentation and retain fail-closed restrictions for the development environment.
5. Add missing metric definitions, source metadata, and unavailable/not-calculated states to API/UI outputs.
6. Expand CI with lint/type/security/coverage checks without reducing existing test coverage.
7. Validate backup/restore, dashboard permissions, and frontend/backend contracts.

## 7. Limitations of this audit

- No real exchange connection or order execution was attempted.
- No production deployment, browser end-to-end session, or live database recovery was performed.
- No local test run was performed by this audit; the CI evidence above is historical GitHub Actions evidence.
- The findings are prioritized code-review observations. Each proposed correction needs focused regression tests before being classified as TESTED or VERIFIED.

**Priority order:** correctness → safety → reliability → feature preservation → intelligence → performance → UI/UX.
